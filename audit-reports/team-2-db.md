## 6. Audit Methodology & Limitations

**Methodology**:
1. Opened every `*.db` file in readonly mode with `bun:sqlite`
2. For each table, ran `PRAGMA table_info`, `PRAGMA index_list`, `PRAGMA index_info`, `PRAGMA foreign_key_list`, and `SELECT COUNT(*)` 
3. Extracted `CREATE TABLE` SQL from `sqlite_master` for inline UNIQUE/PK verification
4. Compared actual schema against `prisma/*.prisma` schema files
5. Grepped source code (`src/`, `scripts/`, `data_engine/`, `news-agent/`, `mini-services/`, `models/`) for `FROM/INTO/UPDATE/DELETE FROM/JOIN <table_name>` patterns via ripgrep
6. Counted read vs write references per table
7. Identified cross-DB table-name duplicates by joining on table name

**Limitations**:
- Code-reference counts for tables that exist in MULTIPLE DBs (e.g., `predictions`, `cached_analysis`, `gold_prices`, `prediction_logs`, `ExpertRecommendation`) are AMBIGUOUS — the regex matches the table name but not the DB file. To disambiguate, one would need to trace each code path's DB connection (e.g., `better-sqlite3('db/stocks.db')` vs `better-sqlite3('db/predictions.db')`). This was OUT OF SCOPE for this audit. The audit confirms DUPLICATION exists; resolution requires per-file tracing.
- The app was actively running during the audit, causing:
  - `auth.db.User` grew from 3 → 4 → 8 rows during the audit window
  - `paper_trading.db` was created mid-audit
  - `predictions.db` gained a 21st table (`prediction_lessons`) mid-audit
- Row counts are point-in-time snapshots, not authoritative.
- Python code references (in `data_engine/`, `news-agent/`, `mini-services/`) may use different table-access patterns (e.g., `cursor.execute("SELECT * FROM " + table)`) that the regex may not catch perfectly.
